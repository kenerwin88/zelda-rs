# Portable dungeon projects

`dungeon-project` makes modern Rust/JSON definitions the source for all 320
dungeon rooms. After the initial export, building and editing the project no
longer needs the original pack or ROM. The output remains a compatibility pack
for the existing runtime; the runtime has not switched to native records yet.

## Export once, build without the original

```sh
cargo build -p zelda3-map-tools

target/debug/dungeon-project export \
  --base-pack target/room-authoring/base.dat \
  --out target/room-authoring/my-dungeon-project

# No --base-pack or ROM is supplied from this point onward.
target/debug/dungeon-project build \
  --project target/room-authoring/my-dungeon-project \
  --out target/room-authoring/from-modern-sources.dat
```

For an untouched export, `byte_identical` must be `true`. The whole pack,
including unrelated assets, header bytes, alignment padding and trailing data,
must match. Build outputs and project directories are create-only.

The project contains:

| File | Role |
| --- | --- |
| `world.json` | Versioned, typed dungeon definitions and shared resources; the canonical content |
| `compatibility/manifest.json` | Original allocations, pointer sharing, source hashes, and explicitly unused spans |
| `compatibility/pack-shell.bin` | Pack container and unrelated assets; all 55 modeled dungeon assets are entirely zeroed |

The shell cannot supply the room content as a fallback. The compiler requires
every modeled byte to be generated by a source or an explicitly unused span,
and rejects disagreeing writes to shared bytes. The tested real pack has **zero
unused spans**: all bytes in the 55 dungeon assets are generated from the model.

These assets are indexes 3–55 and 58–59: room programs, headers, door indexes,
chests, telepathy messages, damaging pit lists, entrances, starting points,
default layouts, overlay commands, secrets, attribute themes and data, movable
blocks, torches and the copied torch-tail words, and actor streams/indexes.
Graphics, audio, enemy damage, and other assets retain their existing formats
inside the shell. Runtime-defined object behavior remains in the engine.

## Edit through Tiled

```sh
target/debug/dungeon-project export-tiled \
  --project target/room-authoring/my-dungeon-project \
  --out target/room-authoring/project-maps
```

Open the `.tmj` maps or `dungeons.world` in Tiled. Move existing objects or
actors, save, then import all edited maps into a new project revision:

```sh
target/debug/dungeon-project import-tiled \
  --project target/room-authoring/my-dungeon-project \
  --world target/room-authoring/project-maps/dungeons.world \
  --out target/room-authoring/my-dungeon-project-v2

target/debug/dungeon-project build \
  --project target/room-authoring/my-dungeon-project-v2 \
  --out target/room-authoring/my-dungeon-v2.dat
```

Use `--map PATH.tmj` instead of `--world` to import a single room. Maps are bound
to the project's current compiled content hash. Import a batch of edits with
`--world`; after importing, export maps again from the new revision before the
next editing round. This prevents an old map from overwriting newer changes.
Tiled import retains its position-only checks and rejects edits to storage
shared with other rooms. Names and other editor-only annotations stay in Tiled;
they do not become runtime data in `world.json`.

## Generate artwork from a project

The optional preview still needs a ROM for the existing graphics producers.
The dungeon content comes from the project, not from an original map pack.

```sh
cargo build --profile parity -p zelda3-map-tools --features preview
target/parity/dungeon-project preview \
  --project target/room-authoring/my-dungeon-project-v2 \
  --rom /path/to/zelda3.sfc --room 0x104 \
  --out target/room-authoring/project-house-preview
```

Open its `room.tmj` in Tiled. It has the same generated artwork, collision
overlays and stale-preview checks as the [preview workflow](tiled-dungeon-maps.md#artwork-and-collision-previews).
Import this map back with `dungeon-project import-tiled --map`.

## Model and validation

`crates/zelda3-map` contains the portable `DungeonWorld`, `RoomDefinition`,
`RoomSettings`, object/actor programs, doors, navigation, rewards, secrets,
overlays, and related records. It depends only on Serde, with no engine,
filesystem, ROM or legacy codec dependency. It validates content references,
IDs, field ranges, control commands and reserved encodings on its own.

`world.json` uses `zelda3_dungeon_world_v1`. Unknown versions and unknown fields
are errors. No implicit migration from the older, incomplete single-room JSON
is performed: export a complete project from its pack. Subsequent format changes
must add an explicit version migration before accepting older source schemas.

Ordered vectors preserve execution order. Room IDs, not the order of the room
list, determine table entries. Shared programs/headers/actors have explicit IDs;
editing a shared resource intentionally affects every room referring to it.
Separate compatibility checks protect partially overlapping storage, such as
door references into a program suffix. Door edits may require updating both
consistent views of a shared byte; the compiler never selects a winner silently.

Room objects retain the three engine object families. Overlay commands have a
separate type because their x/y decoding differs from room objects. Signed floor
and palace fields, unused header/coordinate bits, sprite control records,
empty versus absent door sections, and torch placeholders retain all bits.
Undecoded logical values are explicitly named (`position_word`, `reserved_bits`,
etc.) instead of being assigned an invented meaning.

The compatibility exporter currently requires the original encoded allocation
lengths. It does not relocate or grow streams. Advanced edits to typed fields
can compile when their encodings fit and remain consistent; this validates data
structure, not collision safety, reachability or custom gameplay. The Tiled
adapter remains the more constrained position-editing interface.

## Verification

```sh
cargo test -p zelda3-map-tools -p zelda3-map
ZELDA3_ROOM_TEST_PACK="$PWD/target/room-authoring/base.dat" \
  cargo test -p zelda3-map-tools --test project real_portable_project \
  -- --ignored --nocapture
```

Tests rebuild after deleting a temporary original input, assert that modeled
shell assets are zero, preserve unrelated bytes and nonzero unused spans,
check exact edited bytes, reject malformed/shared/growing content, and exercise
the complete project → Tiled world → project round trip. The real-corpus test
compares the entire pack and checks a house-pot edit against the existing codec.

These are source and compatibility proofs. Native runtime consumption and cold
Snes9x gameplay/video/audio verification remain the next migration boundary.
