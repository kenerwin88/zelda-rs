Modern Audio: Next Big Improvement

The strongest next move is to finish the SFX asset boundary: one reviewed, versioned authoring source compiled into compact runtime data.

Date: 2026-07-13Topic: modern-audio-next-improvementMode: repo-grounded
12 candidates6 survivorsTop confidence: 96%

Grounding Context

The music catalog already follows the desired pattern: a compact, reviewable TSV is validated and packed at build time, while the runtime Rust module is a small typed decoder. SFX has not completed that migration. modern_sfx_catalog.rs is 10,527 lines, the generated full-route Rust include is another 7,653 lines, and exact SFX behavior is split across generated Rust, DSP TSV, pitch TSV, curated constants, and an offline promotion manifest.

The standard route and semantic conformance gates are strong, snapshots are portable, and the oracle runtime is isolated. That shifts the highest leverage from proving one more route to removing duplicated SFX truth and making reviewed assets the thing the runtime actually consumes.

External grounding is modest but supportive: Cargo explicitly supports build-time code generation, and typed Serde deserialization is a conventional way to validate human-readable authoring data before packing it. The repository already uses this exact pattern successfully for music.

1. Unified reviewed SFX asset compiler

Reviewed versioned SFX source
→
Build-time validator and packer
→
Small typed runtime decoder
Description
Make one checked-in SFX asset file the canonical source for program steps, exact DSP parameters, pitch changes, context signatures, names, hashes, and promotion status. The build validates it, rejects non-review-ready runtime entries, and packs it into compact bytes consumed by a small decoder.
Axis
Authoring and review
Basis
direct: SFX truth is currently split across a 10,527-line Rust catalog, a 7,653-line generated Rust include, two TSVs, and an offline manifest whose reviewed subset is not yet the runtime source.
Rationale
This removes the largest remaining duplication, makes review status enforceable, shrinks runtime source, and turns future parity discoveries into data changes instead of Rust surgery.
Downsides
Requires a careful lossless schema and migration parity gate; choosing JSON versus TSV is secondary to defining one canonical typed model.

2. Modern-owned instrument sample pack

Description
Promote BRR sample bytes, loop metadata, and instrument directory entries into a reviewed modern asset pack so playable audio no longer depends on SPC-shaped sample RAM as its data container.
Axis
Runtime independence
Basis
direct: the modern renderer is independent of the SPC interpreter but still models original sample-directory and BRR data.
Rationale
This completes the conceptual separation between modern playback assets and the oracle's machine-state layout.
Downsides
Higher migration risk than the SFX compiler and should follow a stable SFX schema.
Confidence
88%
Complexity

3. Route-independent command generation

Description
Generate legal engine music/SFX command sequences and context transitions, then require deterministic rendering, zero unknown commands, bounded voices, and snapshot-continuation equivalence.
Axis
Coverage and validation
Basis
direct: semantic scenarios already prove commands can be injected without replay-frame coordinates, but the matrix is hand-selected.
Rationale
It finds context combinations that no recorded route happens to exercise and directly addresses the concern that behavior not be hardcoded to one replay.
Downsides
Needs a validity model to avoid spending time on impossible command combinations.

4. Audio parity workbench

Description
Build a small offline report that aligns engine events, voice lifetimes, waveform deltas, and catalog provenance around the first mismatch, with optional short A/B WAV exports.
Axis

Rationale

5. Strict no-fallback release policy

Description
Keep heuristic fallback only behind an explicit development diagnostic switch; release builds reject or silence unknown commands with a precise error and telemetry.
Axis
Failure policy
Basis
direct: current docs still describe a marked heuristic fallback even though covered gates require zero fallback.
Rationale
It prevents missing catalog coverage from masquerading as acceptable audio.
Downsides
Must land after asset coverage is represented canonically or it could turn rare gaps into harsh user-visible failures.

6. Compact semantic PCM fixtures

Description
Store short, named golden PCM windows for engine-level scenarios and verify exact or tolerance-bounded output across platforms.
Axis
Coverage and validation
Basis
reasoned: route digests prove long executions, while small fixtures localize renderer regressions and make failures reproducible without a million-frame run.
Rationale
This makes audio output tests faster and easier to diagnose.
Downsides
Golden audio can be brittle across deliberate renderer changes and platform arithmetic unless its contract is explicit.
